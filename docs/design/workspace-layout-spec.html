1 · Panes

A workspace has three panes: conversation, canvas and terminals, in three fixed places: left (full height), right top and right bottom. That is a small, predictable model, not a free tiling layout.

2 · Terminals

What a terminal is

  • A real shell: your login shell ($SHELL -l, zsh) on a pseudo-terminal in the host, started in the workspace folder. Interactive programs work: vim, htop, claude, tmux attach.
  • Bun 1.4 has the pseudo-terminal built in (Bun.spawn with terminal), so no native module is needed. Checked on this Mac: real tty, resize and input all work.
  • Dark in both themes, like the statusline strip, with the same Nerd Font stack so prompt glyphs render.

Tabs and splits

  • ＋ opens a new tab with one shell. A tab is named after the title the shell sets, or "zsh", "zsh 2" and so on.
  • ◫ Split adds another shell beside the others in the tab (up to 4), with resizable dividers between them.
  • × on a tab closes its shells; × in a split's corner (shown on hover) closes that one. Both ask again in place, like deleting a conversation. exit or ⌃D closes that one terminal; the tab closes with its last terminal.

Which terminals you see

  • Terminals belong to a workspace. The pane shows the terminals of the current workspace (the one of the selected conversation). Switching workspace switches the set; the others keep running (decision 2).

How long they live

  • Shells live in the host. Reloading the page or closing and reopening the window reattaches: the host keeps the last ~256 KB of output of each terminal and replays it.
  • Two windows show the same terminals; tabs and splits are kept in the host too. How wide each split is stays with the window.
  • Restarting the host ends every shell.

Keyboard

A focused terminal gets every key except Mirador's ⌘ shortcuts (⌘K and the others); ⌘C and ⌘V copy and paste. New commands: Toggle terminals, New terminal tab, Split terminal, Focus terminals, in the ⌘K palette and on keys that fit web/shortcuts.ts. Plain-browser limits apply (Chrome keeps ⌘T for itself), so the exact keys get decided while building.

The risk: the terminal renderer in the app's web view. The obvious renderer is xterm.js. Inside Mirador.app it drew the statusline blank. The suspected cause, never confirmed, is that xterm pauses drawing while its IntersectionObserver thinks it is off screen. The statusline was fixed by dropping xterm, and Chrome and Playwright's WebKit don't reproduce the problem. So phase 2 is one bare terminal that you check in Mirador.app before anything is built on top. If it is blank there, the fallback is a fix or workaround for xterm's visibility check, or ghostty-web (Ghostty's terminal compiled to WebAssembly, with an xterm.js-compatible API; its maturity is unverified).

3 · ! commands in the message box

You type
!git status -s
The message box shows it is in shell mode.
→
Host runs it
$SHELL -lc '…' in the workspace folder, without input. Works while the agent is busy, and with Claude Code and opencode alike.
→
A card in the conversation
Command, live output and exit code, styled like the agent's shell cards, with Stop.
→
Your next message
Carries the command and its output to the agent, as Claude Code's own ! does (decision 1).
❯ git status -s M web/Hint.tsx ?? e2e/hints.spec.ts exit 0 · 0.1s
1 command output goes with your next message ✕ A chip in the message box. ✕ drops the output. Output over ~30k characters goes to the agent cut down to its start and end; the card keeps all of it.

The host adds the text to the prompt in Claude Code's own <bash-input>, <bash-stdout> and <bash-stderr> tags, so the agents need no support for it. For interactive programs, use the terminal pane.

4 · Host design

host/terminals.ts (new)

  • Opens, writes to, resizes and closes shells. Keeps each workspace's tabs.
  • Each terminal has a streaming text decoder, so a UTF-8 character split across two reads isn't mangled, and a 256 KB scrollback ring.
  • Output goes only to sockets attached to that workspace. It is never written to host.log or the store.

Protocol additions (shared/protocol.ts)

Browser → host

terminals.attach · terminal.open · terminal.input · terminal.resize · terminal.close · conversation.run-command · conversation.stop-command · conversation.drop-command-output

Host → browser

terminals.listed (tabs and splits) · terminal.output · terminal.replay · terminal.exited. Command cards travel as ordinary conversation events.

5 · Security

  • Nothing new is exposed to the network. The host still listens only on 127.0.0.1, and the websocket still requires the app's Origin and the token cookie.
  • But the token now gives direct shell access as you. Today it gives that indirectly, through an agent and, in YOLO mode, without being asked. The token stays out of logs and URLs (vcs-twf tokenised URL in host.log and vcs-bge token in browser history become more important).
  • The phone bridge never relays terminal.* or ! command messages (vcs-n9r.5 phone bridge). That is a written allow-list there, with a test, not an accident.
  • A page shown in the canvas (its own origin) still can't open the websocket. A new e2e proves it can't open a terminal.

8 · Decisions (2026-10-01)

1. A ! command's output goes with your next message to the agent, automatically, with a ✕ chip to drop it, as Claude Code does.
2. Terminals are per workspace, started in its folder and switching with the selected conversation.
3. Each workspace has its own pane arrangement, with a default picked in a new ⚙ Settings dialog. How the default is picked (thumbnails of the six arrangements, plus whether canvas and terminals start hidden) is my reading of "a default in settings"; tell me if you meant something else.
4. Conversations as tabs in the conversation pane come later, as their own step.
